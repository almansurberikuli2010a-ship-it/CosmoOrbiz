# Cosmo Orbiz — ИИ-оценка риска столкновения спутников

Нажимаешь на спутник → получаешь уровень риска:
**Безопасный / Низкий / Средний / Высокий** и список объектов, которые ему угрожают.

## Сайт

3D-Земля со всеми объектами каталога (положения считаются в браузере по SGP4), вид от
первого лица у выбранного спутника, индикатор риска от нейросети и список реальных угроз
по точному расчёту (с кем, когда, промах, скорость, вероятность; угрозы отмечены в 3D);
факты о космическом мусоре с источниками; анимация синдрома Кесслера, которая
проигрывается прокруткой; раздел «Как это работает» с честными метриками модели.
Также: раскраска глобуса по оценке нейросети или по точному расчёту с фильтром «только
средний и высокий риск»; перемотка к моменту сближения с угрозой (время замедляется возле
сближения, видно расстояние в реальном времени); подборка спутников Казахстана; раздел
«Сегодня на орбите» — группировки в зоне риска и матрица «нейросеть против физики» на
сегодняшних данных (`/api/risks`, `/api/stats`, `/api/kazakhstan`).
Языки: русский, английский, казахский.

```
web/      фронтенд: React + Three.js + satellite.js (Vite)
server/   бэкенд: FastAPI — каталог, TLE для браузера, оценки модели
```

**Запуск на своём компьютере** (из корня проекта):

```bash
cd web && npm install && npm run build && cd ..
python3 -m uvicorn server.app:app --port 8000
```

Сайт откроется на http://localhost:8000. При первом запуске сервер скачивает свежий каталог
с CelesTrak (`data/site/`), а нейросеть за несколько минут оценивает все спутники; результат
сохраняется и после перезапуска подхватывается сразу. Пока оценка идёт, спутник оценивается
по клику (~1 с).

Для разработки фронтенда с мгновенной перезагрузкой: в одном терминале сервер (команда выше),
в другом — `cd web && npm run dev` (http://localhost:5173, запросы `/api` уходят на порт 8000).
Node.js в этом проекте установлен в `~/.local/node`: если `npm` не находится, выполните
`export PATH="$HOME/.local/node/bin:$PATH"`.

Настройки сервера — переменные окружения (описаны в `server/store.py`): `ORBITAL_OFFLINE=1`
(не скачивать каталог), `ORBITAL_BATCH=0` (не оценивать все спутники в фоне — меньше нагрузки),
`ORBITAL_BATCH_SIZE` (меньше — меньше памяти).

## Как это устроено

```
CelesTrak (орбиты)  →  каталог объектов  →  признаки спутника (мгновенно)  →  MLP  →  уровень риска
                                         ↘  точный поиск сближений на 48 ч  →  метки для обучения
                                                                              и список угроз для 3D
```

1. **Каталог.** Орбитальные элементы всех действующих спутников и облаков мусора с CelesTrak.
2. **Метки (учитель).** Для каждого спутника честно просчитываем движение всех объектов
   на 48 часов вперёд (SGP4, шаг 10 с), находим сближения ближе 5 км и считаем
   вероятность столкновения Pc. У TLE нет данных о точности, поэтому по умолчанию
   берётся **максимально возможная Pc** (худший случай), как в сервисе SOCRATES на CelesTrak:
   Pc_max = R² / (e·d²), где d — промах, R — сумма радиусов объектов.
   **Считаются только внешние угрозы.** Сближения внутри одной группировки (Starlink–Starlink,
   OneWeb–OneWeb…) и состыкованные объекты (корабль у МКС: промах и скорость ≈ 0) в метку
   не идут: их координирует оператор, а по TLE они выглядят опасными. Без этого фильтра
   97.5% всех сближений — Starlink–Starlink, и модель учила бы плотность Starlink, а не риск
   (см. `label_experiment.py`, настройка `LABEL_INTRA_GROUP` в `config.py`).
   Максимальная Pc за 48 часов → класс риска:

   | Класс | Pc |
   |---|---|
   | Полностью безопасно | < 1e-7 (или нет сближений) |
   | Низкий | 1e-7 … 1e-5 |
   | Средний | 1e-5 … 1e-4 |
   | Высокий | ≥ 1e-4 (порог, с которого обычно планируют манёвр) |

3. **Признаки (ученик).** 32 признака, которые считаются намного быстрее полного скрининга:
   высоты и наклонение орбиты, свежесть данных, сколько объектов (и сколько из них мусора)
   летает в том же слое высот, оценка скорости встречных объектов, ближайший сосед прямо сейчас,
   **MOID** — сколько орбит проходит ближе 1 / 5 / 20 км от орбиты спутника,
   **группировка** — входит ли спутник в группировку и сколько «своих» рядом,
   **фазировка** — MOID говорит, что орбиты пересекаются, а фазировка — *когда* оба объекта
   окажутся у линии пересечения. Раз в час берутся точные положения (SGP4), по времени прохода
   узлов оценивается промах. Это дало модели «движение»: AUC для Starlink 0.62 → 0.79.
4. **MLP** учится по быстрым признакам предсказывать результат дорогого расчёта.
   Поэтому нейросеть здесь полезна: точный расчёт — минуты, модель — миллисекунды.

## Запуск по шагам

```bash
python data_download.py                  # 1. скачать орбиты -> data/catalog.csv
python build_dataset.py --snapshots 3    # 2. датасет -> data/dataset.csv (долго, см. ниже)
python train.py                          # 3. обучить MLP -> models/, reports/
python predict.py 25544 --screen         # 4. риск для МКС + список угроз
```

На macOS команда называется `python3`, а не `python`.

Если `build_dataset.py` пишет «Спутников для датасета: 0» — значит, не скачалась группа
`active` (действующие спутники), и в каталоге только мусор. Запусти
`python3 data_download.py --force` и посмотри, какую ошибку он пишет для `active`;
теперь при сбое он сам пробует набор групп поменьше.

**Без интернета** вместо шага 1: `python make_synthetic_catalog.py` — синтетический каталог
(~8 тыс. объектов) для проверки, что всё работает. Для настоящей модели нужны реальные данные.

### Сколько это считается

Реальный каталог — десятки тысяч объектов, только Starlink — больше 9 тысяч спутников.
Полный датасет может считаться десятки минут. Для первого прогона:

```bash
python build_dataset.py --max-targets 1500 --hours 24
```

Параметры (окно прогноза, шаг, радиус, пороги классов, размеры объектов) — в `config.py`.

Поменял что-то в `features.py`? Не нужно заново считать сближения:
`python build_dataset.py --features-only` пересчитает только признаки.

Настройки обучения: `python train.py --hidden 128 64 --alpha 1e-3 --class-weight-power 0.5`
(`--class-weight-power`: 1 — полный баланс классов, по умолчанию; 0.5 — компромисс; 0 — без весов).
На реальных данных полный баланс лучше: без него модель вообще не предсказывает «Высокий».

## Как читать результаты обучения

`train.py` печатает таблицу сравнения:

- **macro-F1** — среднее качество по всем 4 классам (главная метрика);
- **опасн.→безоп.** — доля спутников со средним/высоким риском, которых модель назвала
  безопасными. Это самая опасная ошибка, её нужно держать как можно ниже;
- **±1 ур.** — доля ответов, ошибившихся не больше чем на один уровень;
- MLP сравнивается с «всегда самый частый класс» и логистической регрессией —
  если MLP не лучше, значит признаки или данные надо улучшать.

**Текущая модель v4 (полный каталог CelesTrak, октябрь 2026).** Все 16 785 действующих
спутников, 4 снимка с шагом 60 часов (21–31 октября) — 67 136 примеров, опасных 9.8%.
Тест — 13 431 пример по спутникам, которых модель не видела:

| Метрика | Значение |
|---|---|
| macro-F1 | 0.436 (логистическая регрессия 0.431, «всегда самый частый класс» 0.183) |
| опасный назван безопасным | 4.6% |
| AUC «опасный / нет» | 0.81 |
| 10% / 30% спутников с высшей оценкой содержат | 44% / 71% всех опасных |
| точность классов «Средний» / «Высокий» | 17% / 11% |

Модель — хороший **фильтр**: быстро ранжирует, кого проверять. Но у классов «Средний» и
«Высокий» много ложных тревог, поэтому на сайте рядом с оценкой нейросети показан
вердикт точного расчёта и список реальных угроз.

Почему v4, а не прежняя v3: v3 обучали на неполном каталоге — тогда с CelesTrak не скачалась
группа `active`, и не хватало 3 535 спутников (Kuiper, Qianfan, Hulianwang и др.). На полном
каталоге v3 сильно переоценивала риск (42% спутников «Средний»/«Высокий» при реальных 10%,
AUC 0.76). Прежние версии лежат в `archive/`.

В `reports/` — матрица ошибок и кривая обучения (картинки для презентации).

## Честные ограничения (стоит упомянуть на защите)

- Точность TLE/SGP4 — порядка 1 км в сутки, ковариаций в TLE нет. Поэтому Pc — оценка
  худшего случая (консервативная). Операторы используют точные ковариации из CDM.
  Альтернатива: `PC_METHOD = "sigma"` в `config.py` — гауссова ошибка, растущая с возрастом
  данных (`SIGMA_KM`); тогда пороги классов стоит подобрать заново.
- Радиусы объектов заданы по типу (спутник 3 м, ступень 4 м, обломок 0.5 м).
- Класс «Высокий» в реальности очень редкий — для обучения полезно собрать несколько снимков
  (`--snapshots`) в разные дни.

## Как улучшить модель

1. Реальные данные вместо синтетики (`data_download.py` + `pip install sgp4`).
2. Больше снимков в разные дни (`--snapshots 10 --snapshot-gap 24`) — больше редких классов.
3. Модель на уровне **пар объектов**: вход — промах, скорость, геометрия одного сближения,
   выход — риск. Точнее, но требует расчёта сближений (см. первоначальный план).
4. Данные ESA Kelvins Collision Avoidance Challenge — реальные CDM с ковариациями.

## Хостинг на Render

Сайт и API работают одним процессом. Всё описано в `render.yaml` (Blueprint):

1. Соберите фронтенд: `cd web && npm run build` — папка `web/dist` идёт в репозиторий,
   поэтому Node.js на сервере не нужен.
2. Загрузите проект в GitHub. `.gitignore` уже настроен: в репозиторий попадут код,
   `web/dist` и модель `models/orbital_shield_mlp.joblib`, а данные и архивы — нет.
   Каталог сервер скачает с CelesTrak сам.
3. На render.com: **New → Blueprint** → выберите репозиторий. Render прочитает `render.yaml`.

Версии пакетов в `requirements.txt` закреплены: модель сохранена scikit-learn 1.9.1 и должна
открываться той же версией.

**Память.** Бесплатный тариф — 512 МБ и слабый процессор. Поэтому в `render.yaml`:
- `ORBITAL_BATCH_SIZE=400` — нейросеть оценивает спутники небольшими порциями (полный проход
  займёт дольше, но пока он идёт, спутник оценивается по клику);
- `ORBITAL_THREATS=0` — точный расчёт угроз выключен: скрининг всех спутников на 48 часов
  требует ~0,5 ГБ памяти сверх остального. Панель спутника тогда пишет, что расчёт отключён.

На тарифе с 2 ГБ памяти и больше удалите `ORBITAL_THREATS=0` — заработает всё, как локально.
